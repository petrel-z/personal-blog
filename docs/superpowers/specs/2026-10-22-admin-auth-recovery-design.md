# 后台登录、角色权限与密码恢复修复方案

日期：2026-10-22。状态：用户认可邮箱验证码方向，并要求开发前拆分为小功能；本轮完成任务拆分，尚未修改业务代码或数据库。实施顺序见 [开发路线](../plans/2026-10-22-admin-auth-roadmap.md)。

## 需求与已确认现状

用户确认问题发生在本地，并指出管理员无法登录、角色权限管理不完善、缺少忘记密码功能和验证码刷新问题。随后提出通过邮箱发送验证码找回密码；下述方案按这一方向调整，具体默认值仍为建议。

本地 MySQL `localhost:3306/blog` 可连接。只读检查发现：

- `admin@blog.com`（Administrator）存在、未删除、密码哈希格式有效，但没有任何角色。
- `1207574452@qq.com` 没有角色，密码哈希长 61 位；当前 bcrypt 实现只接受 60 位，必定校验失败。
- Role 只有 `member`，Permission 与 RolePermission 均为空。
- 现有服务端授权会拒绝无权限账号进入后台，因此数据库未初始化会直接阻断原管理员。
- 已有 `scripts/setup-auth.ts` 可以为指定的已存在账号初始化角色和授权；此次只验证了 `--help`，未运行初始化。
- 用户管理仅支持列出用户、调用公开注册接口添加用户；没有角色字段、角色分配或角色管理接口。
- 登录和注册先单独校验验证码，再提交凭据。验证码校验会消耗验证码，后续业务失败没有自动刷新。
- 验证码 ID 存在 window 全局变量中；手动刷新不清空输入，加载失败不清除旧 ID，也没有处理请求乱序。
- 认证和注册接口没有强制校验验证码；登录失败限制仅有常量，尚未接入认证流程。
- 没有找回密码页面、重置接口、重置令牌模型或邮件发送模块；本地环境未配置邮件服务和 Redis。

管理员具体使用的登录密码未提供，因此“密码格式有效”不代表实际密码已验证。

## 建议的实现范围

继续使用现有 Next.js 14、Auth.js、Prisma/MySQL 和页面样式。以下产品与实现取舍均为建议，尚非用户已确认的决定。

### 1. 恢复本地管理员访问

- 初始化默认 `admin`、`editor`、`reviewer`、`member` 角色及权限目录，并为明确指定的本地账号分配 `admin`。
- 建议恢复目标为现有的 `admin@blog.com`；执行授权写入前需要确定这是用户要恢复的账号。
- 初始化需可重复执行，不覆盖密码、不清空已有自定义授权。显式初始化与日常角色权限编辑分开，日常启动不重新授予已撤销的权限。
- 若实际管理员是哈希损坏的 QQ 邮箱账号，必须通过身份验证后的密码重置或本地操作员恢复流程重新设置密码；不得猜测、截断或自行替换现有哈希。
- 提供本地诊断结果，区分数据库不通、无管理员、密码校验失败和权限不足。

### 2. 补齐角色权限管理流程

- 第一版管理现有四个内置角色，暂不增加任意自定义角色创建与删除；该范围可由用户调整。
- 增加角色管理页，展示角色说明、成员数量及按业务模块分组的权限。
- `admin` 保留全部权限，`member` 不授予后台管理权限；管理员可调整 `editor`、`reviewer` 的业务权限。
- 用户列表展示角色，管理员可为用户分配一个或多个现有角色。明确区分查看用户、创建用户、分配角色和维护权限等操作权限。
- 管理角色与授权接口仅允许当前数据库中的管理员调用；前端菜单和按钮与服务端权限一致。
- 管理员添加用户使用受保护的专用接口，创建用户与分配角色在同一事务中完成。公开注册固定分配 `member`，不接受客户端角色参数。
- 拒绝移除最后一位有效管理员的管理员身份；用事务及数据库锁保证并发请求也不能绕过保护。
- 授权变更记录操作者、目标和变更内容，下一次受保护请求立即按最新授权判断。
- 登录成功后进入首个有权访问的后台页面；无后台权限显示明确提示。验证码失败、凭据失败、系统异常分别显示对应提示。

### 3. 修复验证码及登录重试

- 组件向父表单提供验证码 ID 和刷新能力，移除 window 全局 ID，保证每个表单的图片、ID 和输入配套。
- 手动刷新、验证码错误或过期、凭据验证失败后，获取新验证码并清空验证码输入；保留邮箱和密码便于重试。
- 刷新期间禁止重复提交；加载失败显示重试入口，清除不可用 ID；防止较早请求覆盖较晚请求，释放旧图片对象 URL。
- 登录、公开注册及密码找回的服务端入口强制检查验证码，不能只依赖前端先调用验证接口。
- 使用共享验证码校验服务；验证码限定用途、有效期和一次性消费。同步兼容现有评论验证码调用，避免改动登录后影响评论。
- 建议使用现有 MySQL 保存短期挑战与失败计数，避免本地登录修复额外依赖当前未运行的 Redis。具体表设计在实施计划中确定。
- 接入原有需求“连续 5 次登录失败锁定 15 分钟”，成功登录清除失败计数，并给出可理解的重试提示。

### 4. 增加忘记密码流程

- 登录页提供“忘记密码”，用户输入注册邮箱和图片验证码，收到 6 位数字邮件验证码后，提交邮箱、邮件验证码及新密码完成重置。两类验证码在界面和服务端使用明确的名称及不同用途。
- 建议通过可配置的 SMTP 服务发送邮件；服务商、发件人及配置位置待用户补充。配置项只记录在环境文件，示例文件提供字段说明。
- 邮件验证码使用安全随机数，绑定邮箱及密码重置用途，建议 10 分钟有效、一次使用后失效。数据库只保存带服务端密钥的验证码摘要，不保存或记录明文验证码。
- 重发间隔 60 秒；重发后旧验证码失效。每个验证码最多校验 5 次，耗尽后必须重新申请；另按邮箱与来源 IP 限制发送和校验频率，防止通过反复申请绕过尝试限制。验证次数和消费使用数据库原子操作，不能被并发请求绕过。
- 已存在、未存在和已删除邮箱在申请接口使用相同对外提示，发送限流也不能泄露邮箱是否存在。邮件服务整体配置或连接故障作为系统不可用处理。
- 邮件验证码校验、消费、密码更新和会话撤销标记在同一事务内完成，防止并发重复使用。密码成功重置后撤销该账号已有登录会话。
- 页面展示重发倒计时、验证码过期及重置成功提示；刷新页面不绕过服务端重发间隔。重置页面不在日志或浏览器持久存储中记录验证码、新密码。
- 本地使用捕获邮件的测试传输完成流程测试。真实投递需要可用邮箱与邮件配置，不能用“已输出验证码”代替真实发送成功。
- `admin@blog.com` 是否为用户可收信的邮箱尚不明确；如果不能收信，本地恢复需使用操作员入口，邮箱找回功能供绑定真实邮箱的账号使用。邮箱修改与角色授权分开，不能通过忘记密码接口改变收信邮箱。

## 验证与验收

1. 在本地指定管理员上确认授权初始化结果，并完成实际登录到后台的验证；没有可用密码时如实说明验证范围。
2. 验证游客、member、editor、reviewer、admin 的页面与接口访问；角色或权限撤销后，既有会话下一次请求即失去对应能力。
3. 覆盖普通用户伪造管理员角色、调用角色管理接口，以及并发移除最后一位管理员等拒绝场景。
4. 浏览器验证首次登录、输错密码后重试、验证码过期、快速连续刷新、验证码请求失败与恢复。
5. 覆盖公开注册、后台添加用户与评论验证码的兼容性，公开注册不能获得管理权限。
6. 验证邮件验证码密码重置成功、过期、输错次数耗尽、重发使旧码失效、重复使用、并发消费、未知邮箱、邮件发送失败、频率限制和旧会话失效。
7. 使用隔离数据运行会写入数据库的集成测试；不重置或删除现有文章和用户。完成相关回归测试、类型检查和构建检查。

- 按小功能逐项交付；第一版管理四个内置角色作为当前建议边界，自定义角色另行扩展。
